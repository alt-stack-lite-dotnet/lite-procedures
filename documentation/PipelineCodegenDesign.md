# Pipeline: кодоген vs рантайм — когда что, фоллбеки, взаимодействие

## 1. Критерии: когда генерировать

**Генерируем пайплайн только когда цепочка полностью известна на этапе компиляции.**

| Условие | Генерация возможна? |
|--------|----------------------|
| Цепочка только из `[InterceptWith(...)]` на типе процедуры, без глобальных интерцепторов | ✅ Да |
| Есть глобальные интерцепторы (`AddGlobalInterceptor<T>()`) для этой процедуры | ❌ Нет (порядок и состав известны только в runtime при вызове `Build()`) |
| Используется `AddProcedureWithCustomPipeline<T>(configure)` с лямбдой | ❌ Нет (цепочка задаётся в runtime в `configure`) |
| Процедура из другой сборки, интерцепторы из другой сборки | ✅ Да, если проект с генератором ссылается на обе сборки |

Итого: **кодоген только для процедур, у которых цепочка задана исключительно атрибутами** (и при этом генератор видит эти типы в компиляции).

---

## 2. Когда не генерировать — фоллбек на рантайм

Во всех остальных случаях используется текущая реализация:

- `ProcedurePipeline<TArgs, TResult>` / `AsyncProcedurePipeline<TArgs, TResult>`
- массив `IProcedureInterceptorCore[]` + switch по типу в `RunBefore` / `RunAfter`
- создание через `Activator.CreateInstance(pipelineType, procedure, interceptors)` в `ProcedureRegistration.Register`

Никакого нового API для пользователя: он по-прежнему вызывает `AddProcedure<T>()` или `AddProcedureWithCustomPipeline<T>()`. Решение «генерить или нет» — внутреннее.

---

## 3. Как принять решение внутри библиотеки

### 3.1. Что знает генератор (compile time)

- Все типы из текущей компиляции и referenced assemblies.
- Для каждого типа, реализующего `IProcedure<,>` / `IAsyncProcedure<,>`:
  - атрибуты `[InterceptWith(typeof(X))]` → упорядоченный список типов интерцепторов **только из атрибутов**.

Генератор **не** знает:

- вызовы `AddGlobalInterceptor<T>()` и порядок регистрации;
- вызовы `AddProcedureWithCustomPipeline` и лямбду `configure`;
- какой именно набор процедур будет зарегистрирован (можно регистрировать подмножество).

Поэтому генератор может только: **для каждой процедуры P с только атрибутными интерцепторами [I1, I2, …] сгенерировать класс пайплайна** и какую-то метку «этот пайплайн для P с цепочкой [I1, I2, …]».

### 3.2. Что знает рантайм при `Build()`

- Какие процедуры добавлены: `AddProcedure<T>()` или `AddProcedureWithCustomPipeline<T>()`.
- Для каждой процедуры — полная цепочка: глобальные интерцепторы + атрибуты (и для custom — результат `configure`).
- Типы: `ProcedureRegistration(procedureType, interceptorTypes[])`.

Только здесь можно принять решение: **совпадает ли фактическая цепочка с той, для которой есть сгенерированный пайплайн**.

### 3.3. Правило выбора (рекомендуемое)

- Пусть генератор для процедуры `TProcedure` генерирует пайплайн только если на `TProcedure` есть **только** `[InterceptWith(...)]` (никаких глобальных не учитываем в кодогене). Имя сгенерированного типа можно завязать на полное имя процедуры и хэш цепочки из атрибутов, например:  
  `ProcedurePipeline_Generated_{FullNameHash}_{InterceptorChainHash}`.
- В **рантайме** в `ProcedureRegistration.Register`:
  1. Вычисляем фактическую цепочку: `interceptorTypes` (уже с глобальными и custom).
  2. Если для этой процедуры **нет** глобальных и **не** использовался `AddProcedureWithCustomPipeline`, то цепочка = только атрибуты. Тогда проверяем: **есть ли в текущей сборке сгенерированный тип пайплайна для (ProcedureType, эта цепочка)**.
  3. Если **да** — создаём пайплайн через сгенерированный тип (рефлексия один раз: `Type.GetType(generatedName)` или заранее зарегистрированный маппинг тип → сгенерированный тип пайплайна).
  4. Если **нет** (цепочка другая, или сгенерированного типа нет) — **фоллбек**: как сейчас, `ProcedurePipeline<,>` / `AsyncProcedurePipeline<,>` + `Activator.CreateInstance(pipelineType, procedure, interceptors)`.

Проблема: как в runtime узнать «есть ли сгенерированный тип»? Варианты:

- **A) Генератор дополнительно генерирует статический класс с регистрацией**, например `GeneratedPipelineRegistry.Register(IServiceCollection, ...)` или маппинг `(Type procedure, Type[] interceptors) → Type pipelineType`, и основной пакет при инициализации вызывает этот метод (если такой тип есть). Тогда в `ProcedureRegistration.Register` мы смотрим в этот маппинг.
- **B) По конвенции имени**: сгенерированный тип в известном namespace, имя = `ProcedurePipeline_Generated_<ProcedureFullName>_<ChainHash>`. В runtime по `ProcedureType` и `interceptorTypes` считаем ожидаемый chain hash (только атрибуты), ищем тип по имени. Минус — зависимость от имени сборки/namespace.
- **C) Генератор генерирует только классы пайплайнов**, а в том же проекте генерируется метод расширения или класс с словарём `Dictionary<(Type, string chainKey), Type>`, заполненным на этапе генерации. При старте приложения этот словарь уже содержит все сгенерированные пайплайны. В `ProcedureRegistration` проверяем ключ (procedureType, chainKey) и при совпадении берём тип из словаря.

Оптимально по надёжности — **вариант A или C**: явный маппинг (procedure + chain) → generated pipeline type, заполняемый кодогеном; runtime только делает lookup и фоллбек.

## 4. Взаимодействие API (один вход — два пути)

Пользовательский API не меняется:

- `AddProcedure<TProcedure>()`  
  → цепочка = глобальные + `[InterceptWith]` на TProcedure.  
  → Если глобальных нет и цепочка совпадает с сгенерированной — используем сгенерированный пайплайн; иначе — рантайм.
- `AddProcedureWithCustomPipeline<TProcedure>(configure)`  
  → цепочка задаётся в runtime.  
  → Всегда рантайм-пайплайн.

Дополнительно можно ввести опцию (глобальную или на билдер):

- `builder.UseGeneratedPipelinesWhenPossible(bool)` — по умолчанию `true`: при совпадении цепочки использовать сгенерированный тип; при `false` — всегда рантайм (удобно для отладки или A/B).

## 5. Фоллбеки по сценариям

| Сценарий | Поведение |
|----------|-----------|
| Процедура только с `[InterceptWith]`, сгенерированный пайплайн есть | Используем сгенерированный класс. |
| Процедура только с `[InterceptWith]`, сгенерированного типа нет (например, генератор отключён или процедура из сборки без генератора) | Фоллбек: `ProcedurePipeline<,>` / `AsyncProcedurePipeline<,>`. |
| Процедура с глобальными интерцепторами | Всегда рантайм-пайплайн. |
| AddProcedureWithCustomPipeline | Всегда рантайм-пайплайн. |
| Сгенерированный тип не найден в сборке (опечатка в конвенции, другая версия) | Фоллбек на рантайм-пайплайн. |
| Интерцептор из атрибута не реализует нужный интерфейс для (TArgs, TResult) | Как и сейчас: исключение при первом вызове (или при создании пайплайна, если решим валидировать при регистрации). Кодоген тут не меняет семантику. |

---

## 6. Итоговая схема

1. **Генератор (incremental source generator)**  
   - Находит все процедуры (IProcedure<,> / IAsyncProcedure<,>) в компиляции + referenced assemblies.  
   - Для каждой процедуры, у которой цепочка интерцепторов задана **только** атрибутами `[InterceptWith]`, генерирует класс пайплайна с явной цепочкой вызовов (без массива и switch).  
   - Генерирует маппинг (procedure type + chain) → generated pipeline type (например, статический класс/метод регистрации или словарь), чтобы runtime мог решить «есть ли сгенерированный пайплайн».

2. **Runtime (ProcedureRegistration.Register)**  
   - Строит фактическую цепочку для процедуры.  
   - Если цепочка = только атрибуты и для неё есть запись в маппинге сгенерированных пайплайнов → создаём экземпляр сгенерированного типа (procedure + инжект интерцепторов по порядку).  
   - Иначе — фоллбек: текущая реализация с `ProcedurePipeline<,>` / `AsyncProcedurePipeline<,>` и массивом интерцепторов.

3. **Поведение**  
   - Один и тот же контракт `IProcedurePipeline<TArgs, TResult>` / `IAsyncProcedurePipeline<TArgs, TResult>`; потребитель не видит разницы.  
   - Где возможно — меньше аллокаций и быстрее за счёт кодогена; где нет — прозрачный фоллбек на текущий рантайм-пайплайн.

---

## 7. Реализация (Lite.Procedures.SourceGenerators)

- **Проект:** `sources/Lite.Procedures.SourceGenerators` — incremental source generator.
- **Контракт в основной библиотеке:** `IGeneratedPipelineRegistry`, `GeneratedPipelineRegistryDiscovery.TryDiscover()`.
- **Генератор:** находит в текущей сборке (не в referenced) все типы, реализующие `IProcedure<,>` / `IAsyncProcedure<,>`; для каждого строит цепочку только из `[InterceptWith]`; генерирует класс пайплайна (sync/async) с явными вызовами интерцепторов и класс `GeneratedPipelineRegistry` с `GetGeneratedPipelineType(Type, Type[])`.
- **Ограничения:** процедуры с generic-аргументами (типы `TArguments`/`TResult` как type parameters) пропускаются; генерируются только процедуры из текущей компиляции.
- **Регистрация:** при `Build()` вызывается `TryDiscover()`; в `ProcedureRegistration.Register` при наличии реестра запрашивается сгенерированный тип по `(procedureType, interceptorTypes)`; при совпадении создаётся экземпляр сгенерированного пайплайна, иначе — фолбек на `ProcedurePipeline<,>` / `AsyncProcedurePipeline<,>`.
